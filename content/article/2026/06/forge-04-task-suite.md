一个 Agent 跑通一次 demo，并不等于它真的可靠。

这句话听起来像废话，但在 Agent 开发里很容易被忘掉。我们太容易被一次漂亮的演示说服：模型读了文件，改了代码，测试也绿了，于是系统看起来就“成了”。问题是，Agent 的行为有很强的路径依赖。换一个任务、换一个文件结构、换一个错误类型，它可能就会暴露出完全不同的问题。

Forge 的 v0.3 引入 Task Suite，就是为了让评估从“看一次演示”变成“跑一组可复现任务”。

# Demo 证明可能性，Suite 证明稳定性

Demo 的价值是展示一个机制能工作。比如 v0.1 的 mock demo 可以证明 agent loop 能跑起来；v0.2 的 verifier demo 可以证明自我修复循环有效。

但 demo 通常只覆盖一条精心设计的路径。它更像舞台剧：动作清楚，重点突出，适合教学。Task Suite 则更像小型考试：每个任务有独立 workspace、初始文件、目标描述和验证方式，Agent 必须在这些任务上分别完成。

Forge v0.3 里先放了两个简单的 coding benchmarks：

- 修复 division by zero bug
- 实现 reverse words 逻辑

任务本身不复杂，但结构重要。它让 Forge 开始拥有一个评估框架：不是问“这次看起来怎么样”，而是问“这组任务通过了多少”。

# 隔离 workspace 很关键

Task Suite 还有一个容易被低估的变化：每个任务都在独立临时 workspace 里运行。

这看似只是工程细节，其实是 Agent 评估的前提。Agent 会读文件、写文件、跑命令。如果多个任务共享同一个目录，前一个任务的残留文件、修改结果、缓存状态都可能影响后一个任务。最后你看到的 pass/fail 结果，就不再只代表 Agent 能力，而是混入了环境污染。

Forge 在 v0.3 里做了 CWD sandboxing，让 runner 切换到任务对应的 workspace 执行。这样每个任务都有自己的小世界，读写边界更清楚，结果也更容易复现。

这也是教学上很重要的一点：Agent 不是漂浮在空气里的智能体，它总是在某个 workspace 里行动。理解 workspace，就等于理解 Agent 的行动范围。

# 评估不是只看最终答案

Task Suite 最直接的指标是通过率，但 Forge 并不只关心 pass/fail。

因为 Agent 的学习价值来自过程。一个任务失败了，我们还想知道：

- 它有没有找到正确文件？
- 有没有读测试？
- 有没有调用 verifier？
- 修改是否命中了目标？
- 是模型判断错了，还是工具返回不清楚？
- 是上下文缺失，还是执行环境问题？

这就需要和 trace 结合起来看。Task Suite 给结果，Trace 给原因。一个负责告诉你“有没有过”，一个负责告诉你“为什么没过”。

对教学应用来说，这种组合非常有用。学生不只是看到红绿结果，还能沿着 trace 复盘 agent 的推理和动作。失败不会只是一句“没通过”，而会变成可分析的学习材料。

# MockModel 也可以用于评估框架

Forge 的 suite 支持 mock 模式，这一点延续了前面版本的教学思路。

真实模型当然更接近生产使用，但在开发评估框架本身时，MockModel 能帮我们排除模型随机性。它让我们先验证 suite 逻辑、workspace 隔离、任务初始化、验证命令和汇总报告是否正确。

这背后有一个开发 Agent 系统时很实用的原则：不要把所有变量同时打开。

如果 agent loop、工具执行、模型输出、文件环境、验证逻辑都同时变化，失败时很难判断问题来自哪里。MockModel 让我们先固定模型行为，把系统框架调清楚，再接真实模型。

# 从功能开发走向实验平台

v0.3 是 Forge 演进里的一个分水岭。

在它之前，Forge 更像一个最小 Agent 示例：能运行、能修复、能被 verifier 打回。在它之后，Forge 开始像一个教学实验平台：我们可以定义任务，隔离环境，运行 benchmark，收集结果，复盘 trace。

这一步很重要。因为如果我们想教别人理解 Agent，就不能只展示成功案例。我们还要提供一种方式，让学习者系统地观察成功、失败和修复。

Agent 教育的核心不是让每次 demo 都完美，而是让每次运行都能产生可学习的证据。
