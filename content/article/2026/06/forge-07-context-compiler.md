Agent 跑得越久，上下文就越重。

一开始，message history 很清爽：system prompt、用户任务、一次模型输出、一个工具结果。几轮之后，里面开始堆满文件内容、命令输出、测试日志、错误堆栈、模型解释和工具调用参数。再跑久一点，上下文不仅贵，而且会变得吵。

Forge 的 v0.6 引入 Context Compiler，就是为了回答一个问题：长任务里，Agent 到底应该记住什么？

# 原始记忆和模型上下文不是一回事

很多人会把“保存所有历史”和“把所有历史发给模型”混在一起。Forge 刻意把这两件事分开。

`Context` 里保留完整 message history，作为本地状态、trace 和 checkpoint 的来源。这是原始记忆，不能随便丢。

但 `get_messages()` 返回给模型时，会动态生成一个更轻的版本。旧工具输出可以折叠，旧 assistant thoughts 可以压缩，最近几轮保留更多细节，长输出则做智能截断。

这背后的原则是：系统应该保存完整历史，但模型不一定每次都需要看到完整历史。

这一步对 Agent 很关键。因为模型上下文不是数据库，也不是日志仓库。它是当前决策所需的信息窗口。

# 折叠历史，保留结构

v0.6 的 history folding 很朴素：较老的 tool output 如果太长，就替换成一个占位提示，说明这个输出已折叠以及原始长度；较老的 assistant thought 如果伴随 tool calls，也可以折叠成 `[Thoughts folded]`。

注意，这不是删除历史，而是给模型一个结构性提示：这里曾经发生过一次工具调用，但细节现在不重要。

这种做法非常适合教学。它让学习者看到上下文管理不是简单地“截断前 N 个 token”，而是按角色、时间和用途处理信息。

用户直接说的话、最近的工具结果、可能影响下一步的错误信息，优先级更高；很久以前的长日志，优先级更低。

# Traceback 是长日志里的黄金

v0.6 里最有意思的部分，是 traceback extraction。

测试命令常常会输出大量噪音：初始化日志、连接信息、warning、重复打印。真正对修复有用的，可能只是最后那段 Python traceback。直接截断头尾有时会丢掉关键异常；完整保留又浪费上下文。

所以 Context Compiler 会尝试用正则识别 Python traceback，并在长输出中提取异常块。如果 traceback 本身也很长，就保留最后若干行，因为那里通常包含最具体的错误类型和报错位置。

`examples/demo_context.py` 里模拟了一个场景：测试输出包含大量无关数据库连接日志，但真正的问题是 `AttributeError`。Context Compiler 把噪音压缩掉，保留关键 traceback，让 Agent 仍然能修复问题。

这展示了一个重要直觉：上下文压缩不是为了少，而是为了让关键信息更突出。

# 上下文管理影响智能表现

有时我们觉得模型“变笨了”，其实不是模型能力突然下降，而是上下文污染了决策。

太多无关信息会分散注意力；太早的错误可能误导当前判断；重复日志会挤掉真正重要的文件内容。Agent 系统如果不管理上下文，就会在长任务里逐渐失去方向。

Context Compiler 的价值，就是在原始历史和模型输入之间加一层编译过程。它像一个过滤器，把完整执行历史转换成当前轮次更可用的 prompt。

这也是为什么 Forge 把它叫 compiler，而不只是 truncator。它不是机械裁剪，而是在保留语义结构的前提下重新组织上下文。

# 记忆不是越完整越好

v0.6 想教的不是某个具体压缩算法，而是一种 Agent 工程里的基本判断：记忆要分层。

完整历史应该保存在本地，用于恢复、追踪和审计；模型上下文应该按当前任务动态编译；关键信息应该被提取出来，而不是淹没在日志里。

当你开始这样看 Agent，就会发现很多系统问题都和上下文有关。Agent 忘记了前面的决定，可能是上下文没保留；Agent 抓不住错误，可能是错误被截掉；Agent 反复走错路，可能是旧信息没有折叠。

Forge 的 Context Compiler 只是一个最小实现，但它打开了一个很重要的教学入口：Agent 的智能，很大一部分来自它在每一轮到底看见了什么。
