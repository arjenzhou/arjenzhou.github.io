Agent 最危险的时刻，往往不是它不知道怎么做，而是它以为自己已经做完了。

在普通聊天里，模型说“我完成了”只是一句话；但在 Coding Agent 里，这句话可能意味着系统停止循环、任务结束、代码被交给用户。如果没有外部验证，这个完成状态其实很脆弱。模型可能没有跑测试，可能没发现语法错误，可能只修了表面问题，甚至可能在工具调用失败后仍然自信地宣布结束。

Forge 的 v0.2 加入了 Verifier gatekeeper，就是为了解决这个问题。

# 完成状态不能只由模型决定

在 v0.1 里，Agent 的结束条件很简单：如果模型不再返回 tool calls，runner 就认为任务结束。

这符合很多 tool-calling API 的直觉：有工具调用就继续执行，没有工具调用就返回最终答案。但对 Coding Agent 来说，这个规则太宽松了。因为“没有工具调用”只代表模型决定停下，不代表任务真的完成。

所以 v0.2 改了一个关键逻辑：当模型尝试结束时，Forge 不会立刻相信它，而是先运行 verifier。

Verifier 做两类事情：

- 检查 Python 文件是否存在语法错误
- 运行用户传入的 test command

只有 verifier 通过，runner 才允许 Agent 真正结束。如果 verifier 失败，Forge 会把失败报告重新塞回上下文，让模型继续修。

这就是 gatekeeper 的含义：模型可以申请完成，但系统负责批准完成。

# 自我修复不是一句口号

很多人说 Agent 可以 self-correct，但这个词如果不落到机制上，很容易变成玄学。

Forge 里的 self-correction 很具体：

1. 模型修改代码；
2. 模型尝试结束；
3. verifier 运行检查；
4. 检查失败；
5. runner 把错误报告作为新的 user message 加回上下文；
6. 模型看到错误，再次调用工具修复；
7. verifier 再次检查。

这个循环让“自我修复”变成了一个可观察、可测试的系统行为。

`examples/demo_verifier.py` 里故意设计了一个场景：MockModel 修改代码时制造了语法错误，然后自信地表示任务完成。Verifier 拦住它，把语法错误反馈回去。下一轮模型读到错误，修复代码，最后通过检查。

这比一句“Agent 能根据反馈改正”更有教学价值。学习者可以清楚看到：反馈从哪里来，如何进入上下文，又如何影响下一次决策。

# Verifier 是 Agent 的外部现实

LLM 的输出是语言世界里的判断，测试和编译是工程世界里的判断。Coding Agent 要可靠，必须让这两个世界相遇。

Verifier 扮演的角色，就是外部现实。

模型可以认为一个函数已经修好了，但单元测试会告诉它边界条件有没有覆盖；模型可以认为一段代码格式正确，但语法检查会告诉它是否真的能运行。Verifier 不需要很复杂，它只要足够客观，就能显著改变 Agent 的行为。

这也是 Forge 的一个教学重点：不要把模型当成最终裁判。模型适合提出下一步行动，适合解释错误，适合生成补丁；但完成状态应该尽量交给可执行的检查。

# 用户也应该学会设计 Verifier

如果把 Forge 当作教学应用，v0.2 不只是在教“系统如何验证 Agent”，也在教用户如何给 Agent 设计任务边界。

一个好的 agent task，最好不只有自然语言目标，还应该有可执行验证方式。例如：

- 修复 bug：给出测试命令
- 实现函数：给出单元测试
- 修改文档：给出格式检查或 diff 检查
- 重构代码：给出编译、测试、静态检查

如果没有 verifier，用户只能靠读最终回答判断质量；有 verifier，Agent 的每一步都可以被更具体地约束。

这会改变人和 Agent 的协作方式。用户不再只是“提需求的人”，而是任务环境的设计者。你给 Agent 的不只是目标，还有判断目标是否达成的标准。

# 被打回，是可靠性的开始

从体验上看，Verifier 会让 Agent 更慢。它本来想结束，系统却说“不行，测试没过，继续”。但从工程上看，这个“不行”非常重要。

因为可靠系统不是从不犯错，而是犯错以后能被发现、能被反馈、能被修正。

Forge 的 v0.2 想传达的正是这个直觉：不要害怕 Agent 被打回重做。恰恰是这个被打回的机制，让 Agent 从一次性生成器，变成了可以在现实反馈中迭代的执行系统。
